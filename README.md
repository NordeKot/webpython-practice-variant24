# Практическая работа №1 — вариант 24

Дисциплина: «Прикладная разработка серверных частей веб-приложений
на языке Питон». Группа ИКБО-71-24, 2026/2027 учебный год.

Прототип реализует три этапа варианта 24: модель слоя доступа к данным,
RPC на основе TCP и Model-Based Testing с Hypothesis. Записи хранятся
**только в оперативной памяти, в виде кортежей**. База данных и HTTP-интерфейс
не используются: требуемый транспорт в задании — TCP.

Проверки: [docs/VALIDATION.md](docs/VALIDATION.md).

## Требования и установка

Python 3.10 или новее. Само приложение использует стандартную библиотеку.
Для тестов нужны зависимости из requirements-dev.txt.

Windows: установите Python 3.12 и запустите setup.bat двойным щелчком. Затем откройте терминал
в папке проекта и выполните `run.bat demo`. Для проверки — test.bat.

Linux/macOS:

```sh
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -e . -r requirements-dev.txt
./run.sh demo
```

Проект запускается из исходников, отдельная сборка не нужна.
Сборка устанавливаемого пакета, если требуется:

```sh
python -m pip wheel . --no-deps --wheel-dir dist
```

Созданные артефакты не добавляются в репозиторий.

## Модель и поля

Порядок ниже совпадает с порядком значений в кортежах и JSON-массивах ответа.

| Таблица | Поля по порядку |
| --- | --- |
| Entity | identifier:int, created:int, ip:str, locale:str, platform:str |
| Assignment | identifier:int, created:int, parameter:str, entity:int, tags:str, stage:str, triggered:int |
| Feedback | identifier:int, created:int, output:str, stage:str, exception:str, assignment:int, cache_hit:int, duration:int |

Assignment.entity ссылается на Entity.identifier.
Feedback.assignment ссылается на Assignment.identifier.

Время created и triggered трактуется как Unix-время в секундах.
Идентификатор задаёт вызывающая сторона, он уникален внутри таблицы.
Строка создаётся только с полным набором полей нужных типов; лишние поля
и bool вместо int отвергаются. Строки рассматриваются как обычные str:
формат IP, перечни stage и единица duration заданием не определены.
Каскадного удаления нет: сначала удалить Feedback, затем Assignment,
затем Entity. Отсутствующий ключ, дубликат и отсутствующий родитель — ошибки.
Эти решения документируют поведение, не уточнённое в методичке.

## Все публичные функции и RPC-методы

| Код | Функция / метод | Аргумент | Результат |
| --- | --- | --- | --- |
| 1 | create_entity | record:dict | новая запись |
| 2 | delete_entity | identifier:int | None / null |
| 3 | get_entity | identifier:int | одна запись |
| 4 | list_entity | нет | список записей |
| 5 | create_assignment | record:dict | новая запись |
| 6 | delete_assignment | identifier:int | None / null |
| 7 | get_assignment | identifier:int | одна запись |
| 8 | list_assignment | нет | список записей |
| 9 | create_feedback | record:dict | новая запись |
| 10 | delete_feedback | identifier:int | None / null |
| 11 | get_feedback | identifier:int | одна запись |
| 12 | list_feedback | нет | список записей |
| 13 | recent_feedback | нет | список (parameter, cache_hit, output) |

Model возвращает записи кортежами. JSON не имеет типа tuple, поэтому
RpcClient получает списки. list_* сортирует строки по identifier.
recent_feedback удаляет повторяющиеся строки и сортирует их по repr
для воспроизводимого вывода. Порядок результата реляционной алгеброй
не задаётся, поэтому сортировка — соглашение реализации.

### Соединение варианта 24

Сначала выбрать Feedback с `created > now - 300`, затем выполнить **LEFT JOIN**
по `Assignment.identifier == Feedback.assignment`, затем вывести только
Assignment.parameter, Feedback.cache_hit, Feedback.output без дубликатов.

Если у задания нет свежего отзыва, его строка всё равно попадает в результат
с None / null в двух полях отзыва. Отзыв ровно на границе 300 секунд исключён.
Если свежих отзывов несколько, сохраняются все различные строки проекции.
Фильтр не задаёт верхнюю границу времени: это соответствует формуле задания.

## Примеры использования

В локальном REPL или в клиенте вставляйте по одной строке:

```json
{"method":"create_entity","args":[{"identifier":1,"created":1800000000,"ip":"127.0.0.1","locale":"ru","platform":"Windows"}]}
{"method":"get_entity","args":[1]}
{"method":"list_entity","args":[]}
{"method":"delete_entity","args":[1]}
{"method":"get_entity","args":[1]}
```

Последняя команда демонстрирует ошибку отсутствующей записи.
`exit` завершает REPL. Поддерживается EOF. Ошибка команды не завершает REPL.

Полный пример всех 13 операций, связей и ошибок: `run.bat demo`.
Его JSON-команды можно скопировать в REPL для интерактивной демонстрации.
Для удалённого примера сначала запустите `run.bat server` в первом окне,
затем `run.bat rpc-demo` во втором. В примерах время берётся автоматически,
поэтому отзывы будут свежими независимо от даты запуска.

## Бинарный протокол

Многобайтовые целые передаются **little-endian**, без выравнивающих байтов.
Длина тела — количество байтов UTF-8, а не количество символов строки.

| Запрос | Смещение | Размер |
| --- | --- | --- |
| версия | 0 | 1 байт |
| код операции | 1 | 2 байта |
| размер тела | 3 | 3 байта |
| JSON-массив аргументов | 6 | по размеру тела |

| Ответ | Смещение | Размер |
| --- | --- | --- |
| код операции | 0 | 1 байт |
| размер тела | 1 | 4 байта |
| JSON-ответ | 5 | по размеру тела |

Задание не определяет конкретные коды, версию и форму JSON. В реализации
коды 1..13 заданы таблицей выше; JSON-запрос — массив аргументов метода;
ответ — `{"ok":true,"result":...}` или `{"ok":false,"error":"..."}`.
Ответ повторяет код операции, а при неизвестном коде / неполном заголовке
использует 0. Это позволяет ответить и на 2-байтовый неизвестный код,
который не помещается в 1-байтовое поле ответа.

Один вызов использует одно соединение. recv_exact собирает сообщение
из нескольких recv: TCP может передать его фрагментами. Общая модель
сервера защищена блокировкой. Журнал содержит адрес клиента, заголовок,
аргументы, код операции и результат или ошибку; записывается в stdout.
После остановки сервера данные исчезают. Сервер по умолчанию локальный,
аутентификация и публикация в интернете не входят в это задание.

## Тестирование и покрытие

```sh
python -m pycodestyle --max-line-length=79 src tests
python -m pycodestyle --select=W505 --max-doc-length=72 src tests
python -m ruff check .
python -m coverage erase
python -m coverage run -m pytest -q
python -m coverage report -m
python -m coverage html
```

Coverage настроен на измерение **ветвей**, включая серверные потоки.
Откройте htmlcov/index.html. Сгенерированный HTML-отчёт и служебные файлы
не коммитятся. Итог подготовленного прогона: docs/VALIDATION.md.

В RuleBasedStateMachine клиент взаимодействует с настоящим TCP-сервером,
а эталон использует словари и собственные алгоритмы, без вызова Model.
Hypothesis генерирует входы и последовательности действий. В каждом сценарии
initialize с генерируемыми данными выполняет полный жизненный цикл всех
таблиц, что обеспечивает вызов каждого из 13 методов. После каждого правила
invariant сравнивает состояние всех таблиц и соединение. Проверяются создание,
чтение, удаление, дубликаты, внешние ключи, неверные типы и граница 5 минут.
Время эталона и сервера фиксировано только внутри тестов.

Дополнительные тесты тоже используют Hypothesis: проверяют смещения байтов,
UTF-8, фрагментацию, некорректные запросы, восстановление после ошибок,
REPL и команды запуска. Лимиты MBT: 40 примеров, 35 шагов, без deadline;
derandomize=True для воспроизводимости. Настройки — tests/test_mbt.py.

## Проверка оформления

PEP8 проверяется pycodestyle 2.14.0 по исходникам и тестам без noqa
и дополнительных исключений. Максимальная длина строки — 79 символов,
строки документации — 72 символа (дополнительная проверка W505).
Ruff дополнительно проверяет имена (N), порядок импортов (I), ошибки
кода (F) и цикломатическую сложность не выше 10 (C90).
Эти проверки включены в test.bat и запускаются до функциональных тестов.
Правила вашей учебной системы могут дополнительно ограничивать
когнитивную сложность или задавать собственные пороги. Её конфигурация
нужна, чтобы подтвердить точное совпадение со всеми такими правилами.

## История этапов

Три коммита этапов с Conventional/Scoped Commits после технического
коммита chore(repo), который инициализирует пустой репозиторий:

1. feat(model): модель, кортежи, операции и REPL.
2. feat(rpc): протокол, сервер, клиент, демонстрации.
3. test(mbt): Hypothesis, покрытие, проверки и инструкция.
